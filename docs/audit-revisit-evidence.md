# Append-only audit revisit evidence

Store → Audit History → Original audits & revisit evidence. Admin/Ops select the stable original H&S history entry, enter the revisit date and notes, and upload a PDF, DOCX, JPG, PNG or WebP up to 4 MB. Existing `viewEvidence` roles can read the history and download evidence only after the authenticated store query passes existing RLS. Scoped client roles receive no new access.

The original `fa_store_audit_history.id` is the foreign key. Revisit rows retain the date, note, original filename, verified SHA-256, size, uploader and timestamp. They cannot update/delete existing audits, answers, scores, actions, visit dates/counts or audit PDF pointers. Evidence does not close failures or grant signoff. `saveLatestAuditPdf`, studio publication and ordinary audit-PDF upload paths are not used.

Each upload attempt owns a random private object with `upsert:false`. The server checks file signatures and verifies a downloaded copy's hash before committing the row. Database uniqueness covers both the submission UUID and original/date/hash fingerprint. Retries return the original row; changed metadata conflicts rather than overwriting it. A losing retry removes only its newly uploaded object. Confirmed validation/transaction failures and failed readback attempt cleanup. An ambiguous RPC/network outcome retains the private object, because the row may already have committed; the UI holds the same submission for retry. Any orphan cleanup must compare committed `storage_path` references before deleting objects. There is no automatic orphan deletion or evidence removal endpoint.

## Tracker and revisit queue

The Audit Tracker Follow-up column and mobile cards show evidence date, original audit identity, document count, and authorized evidence/history links. Each row is a document; counts do not claim distinct physical visits. The All evidence link opens Audit History directly.

Valid evidence completes the current revisit visit requirement only when the original audit number, date, score and PDF pointer match the latest completed audit snapshot. Evidence for older audits or replaced PDFs cannot satisfy a newer failed audit. The unplanned Routes queue then omits that completed revisit. Existing planned routes/dates/assignments are retained, and routine second-audit obligations remain separate. Permission/query failure retains the revisit requirement. Dashboard visit labels show Revisit Complete while original scores, risk drivers, open findings/actions and signoff remain unchanged. Upload success revalidates tracker/routes/dashboard/store views. No additional migration is required.


## Private preview and download

Tracker follow-up, store history and dashboard evidence controls open the shared accessible preview dialog. Each opening retrieves fresh bytes through the existing authenticated, store-scoped API; closing cancels the request and revokes the object URL. PDF.js renders saved PDFs on desktop/mobile, and Download saves the same verified blob with a portable filename. Non-PDF images preview inline; other supported documents retain download. Expired/denied sessions, missing evidence, storage failures and invalid/corrupt responses show a retryable error without navigating away. The server verifies size/SHA-256 against immutable metadata before returning a private no-store response. No schema, permission or storage-policy change is required.

`node scripts/test-revisit-preview-ui.mjs` exercises the real dialog/transport/PDF.js with a six-page fictional file, exact downloaded hash/name, error/retry/cancel/reopen, focus/Escape and mobile bounds. It requires an existing production build for CSS and local Chromium. Existing history/follow-up harnesses verify the entry points. Live Dundee acceptance requires an authenticated browser: open its existing evidence from tracker/history/dashboard, check all six pages and compare downloaded bytes with the known original hash. Synthetic tests do not establish the cause of a previously reported live storage failure.

## Replacing a revisit report

Audit managers can choose **Replace report** on the current revisit report, select the corrected file and save it. The original audit and revisit date are fixed during replacement. Notes can describe the correction. **Cancel replacement** discards the unsaved form without writing anything. The current file is shown in the main list; **Previous versions** opens the earlier files and their recorded notes. Previous files use the same authorized preview/download endpoint and hash verification as current files.

A replacement inserts an immutable row with `replaces_id` pointing at the selected version. The migration `20261029133341_version_audit_revisit_evidence.sql` adds a restricted self-reference, a unique successor index and an insert trigger enforcing the same original audit and revisit date. It leaves UPDATE/DELETE rejection, table grants, RLS and the private bucket policy intact. The replacement RPC is security invoker, uses an empty search path, is callable only by service role, and repeats the active audit-manager check. The API still requires `manageAudits` and caller store access for writes, and `viewEvidence` plus caller store access for all current/historical reads. No original audit, score, PDF pointer, action, finding or sign-off is changed.

Each replacement owns a new verified storage object. Submission IDs remain frozen for retries after uncertain responses. A unique successor prevents two competing changes becoming current; a stale or conflicting submission returns 409 and the form reloads history, requiring the manager to cancel and select the current report. An exact committed request can be replayed safely even after a subsequent replacement. The same replacement with a fresh request ID deduplicates while it is current. Reusing an earlier same-audit/date file's content, or changing frozen submission metadata, is rejected instead of creating a second active copy. The existing original/date/content uniqueness remains in force. Only an uncommitted/losing attempt's own object can be cleaned up; a transaction with an uncertain result retains its upload for retry/review.

`currentRevisitEvidence` selects chain tips for both Audit History and the shared follow-up summaries used by tracker, route planning and dashboard. Previous versions remain retrievable but do not increase the document count or appear as extra visits. Separately added revisit evidence remains separate.
